# PSOBB 汉化与单机工具技术笔记

本文依据本地现有实现及 2026-10-28、2026-10-29 的问题记录整理。历史测试是当时的结果；本次 GitHub 整理是否重新执行测试，以仓库发布记录为准。源码存在、离线回读成功和实际游戏通过是不同的证据。

## 4:3 显示、模式枚举与输入检测

检索入口：`launcher.py`、`launcher_display.py`、`launcher_input.py`；原生侧的 `WideScreen.c`、`display_modes.hpp`、`presentation_window.h`、`presentation.hpp`、`d3d8to9_base.cpp`、`d3d8to9_device.cpp`。

当前方案保留 4:3 内部画面。启动器把客户端保持在窗口模式；兼容全屏与无边框使用窗口呈现，避免进入客户端原生独占全屏的失焦退出路径。原生补丁读取客户端同目录 `launcher_display.ini` 的内部尺寸及模式，移除窗口框架、覆盖主显示器，在居中的 4:3 矩形呈现画面，并使用黑色子窗口维护周围黑边。

首版失败的关键经验：只替换客户端分辨率表不够。客户端还会通过 Direct3D8 枚举显示模式；缓存里缺少所选尺寸时，可能记录 `Can't find DisplayMode`、`Can't use format` 并退出。修正通过 `CheckDeviceType(..., windowed=TRUE)` 检查格式能力，再向缓存补入内部尺寸的 X8R8G8B8 / A8R8G8B8 模式，避免重复插入。该补项表示窗口后台缓冲能力，不能解释为显示器支持相应物理独占输出。

局部目标矩形呈现使用 `D3DSWAPEFFECT_COPY`、单后台缓冲且关闭 MSAA；普通窗口保留自己的抗锯齿选项。`Reset` 前释放补丁创建的默认池资源，重置成功后重建。启动器与原生 DLL 必须使用匹配版本。

历史记录包含七种尺寸的模式枚举检查，以及三种尺寸的实际设备创建、主/额外交换链 `Present`、释放资源后的 `Reset` 检查；另有用户在本机确认第三版显示修复可用。这些记录不证明其他电脑、所有切出返回情景或所有控制器均兼容。本次发布不重新宣称完成上述游戏验收。

输入检测通过 XInput 和 WinMM 读取设备状态。WinMM 不是完整 DirectInput 枚举，同一实体设备可能出现两次；检测窗口有响应也不代表游戏内映射已兼容。键盘测试限于测试窗口回调，代码不实现全局键盘监听或输入转换。

## 成长表：保留占位记录和 REL 指针

检索入口：`ConfigManager.scale_ply_level_tbl`、`ConfigManager.apply_stats_multipliers`、`test_level_table_scaling.py`。

已定位的问题是：每职业有 200 条记录，其中第一条是等级 1 的占位记录。旧实现从第一条真实升级记录开始仍处理 200 行，最后一次写入越过成长数据，覆盖 `0x7158` 的职业地址数组。服务端和客户端采用不同的读表方式，可能出现服务端保存了等级、客户端只回血而没有及时更新本地等级，重登后才刷新。

当前实现保持每职业步长 200，仅缩放后续 199 条真实升级成长。针对已知 29,184 字节布局，先校验职业指针数组和 REL 根指针，再从完整的 `.default` 基线生成结果。全 1 倍率直接返回原数据，避免把合法的零成长字段改成 1。不要只比较成长字段：经验阈值、等级 1 占位记录、指针数组及 REL 尾部都应保持预期值。

历史匹配输入记录：

| 输入 | SHA-256 |
| --- | --- |
| `PsoBB.exe` | `cd82b56e04468bd2270330fbce19f7cbf5586e8957f25b8342608f2507a6dfe6` |
| 原成长 BIN 基线 | `59d29b9c510a39965074c45c29b4a1a0f5f7d78d5b156e9d32798aeb9a8386d6` |

这些哈希来自既有诊断记录，用于识别当时底本；它们不代表其他客户端版本受支持。工具不追溯重算已有角色属性。历史离线测试覆盖四组倍率、12 职业、经验阈值、尾部与损坏基线拒绝；反馈玩家使用原角色实际升级后的验收仍应单独记录。

## 红盒概率与 Section ID

检索入口：`launcher_data.py` 中的 `rare_probability`、`adjust_rare_table`、`apply_drop_profile`，以及 `launcher.py` 的配置保存和随机徽章逻辑。

概率编码按本地审计的 Tethealla `ExpandDropRate` 逻辑解释；编码 0 保持禁用，其他编码对应 32 位阈值：

```text
P(code) = ((2 << max(0, (code >> 3) - 4)) * ((code & 7) + 7)) / 2^32
```

底层接口支持 0—30 档：0 恢复基线，其余档位从原始概率向目标插值，并向下选择可表示的编码；原先高于目标的条目不降低。怪物条目之外通常还有普通掉落判定，所以稀有判定率不是每次击杀的最终红盒率。箱子同一区域可能尝试多个条目，代码按区域合计概率分配提升，不能把每条都单独拉到目标后直接相加。

**当前启动器的产品行为已经变化：保存配置时使用 20 档，并允许选择十种掉落 Section ID 或每次开始游戏随机抽取。** 旧文档中的 0—30 滑块操作说明属于早期界面，不应直接当作当前使用说明。底层保留 0—30 参数是为了恢复、测试及复用。

`apply_drop_profile` 处理 EP1/2/4 × 怪物/箱子 × 四种难度 × 十种 Section ID，共 240 张表。选择 Section ID 时替换掉落来源而保留目标表头，不修改角色外观或存档。首次保留 `drop/redbox-original` 基线，后续总从基线计算；状态文件记录原始、已应用及待写入哈希。检测到未知外部修改时拒绝覆盖。单文件使用临时文件加 `os.replace`，整个目录仍不是一个原子事务，写入时不能启动服务端。

历史记录已覆盖真实掉落表的恢复、递增、物品/区域保持及隔离副本的重试、外部修改保护；未完成游戏内掉落统计实测。本仓库不分发这些实际掉落表或备份。

## 0xc0000142 与附加音频层隔离

检索入口：`audio_compat_toggle.ps1`。

`0xc0000142` 表示 DLL 初始化失败，本身不指出具体 DLL。既有排查选择先停用后来加入的 DSOAL 音频兼容层：把已识别的本地 `dsound.dll` 移到 `audio-compat/disabled/`，保留可恢复副本，其余图形链保持不变，以保留单变量比较价值。

工具先检查游戏进程、已知 DLL 哈希与目标冲突，遇到未知版本拒绝移动，不修改系统目录。哈希使用 .NET SHA256，避免依赖当时不可用的 `Get-FileHash` 模块。已知 DSOAL DLL 哈希为 `c304c7c822e885d35d016ef2667ed98bd3c3f688d16c35ce5e412d61749542cf`。

历史隔离测试检查停用、重复停用、恢复、冲突及未知哈希拒绝；没有故障玩家机器上的加载失败证据，不能据此宣布远端故障已解决。DSOAL 是否改善音频也没有被这项隔离测试证明。

## QST、PRS 与原地定长回填

检索入口：`psobb_quest_tool.py` 的 `QSTArchive`、`QuestBytecodeTool`、`prs_compress`、`prs_decompress`；批处理入口为 `psobb_batch_tool.py`。

当前 QST 适配器按 1,056 字节分块处理，块内承载最多 1,024 字节载荷；重新打包同时更新文件描述中的成员长度与每块载荷长度。文本通常来自解压后的 `.bin` 成员；保留 `.dat` 等其他成员内容。仅证明成员内容回读正确，还不足以证明所有容器元数据、未知块种类或游戏加载行为正确。

任务头使用 UTF-16LE 固定区间：标题 `0x18—0x58`、简报 `0x58—0x158`、详述 `0x158—0x39C`；预算分别为 31、127、289 个 UTF-16 码元，另留两个字节给终止符。对白记录保存稳定 `id`、`raw_offset`、`raw_len`、`max_chars` 和译文。回填以实际 UTF-16LE 编码字节数检查硬预算，在译文后写双零终止符，剩余槽位补零，使该槽位和解压后字节码总长保持不变。

当前提取器使用 ASCII 范围 UTF-16LE 字符串的正则扫描，并非完整任务字节码反汇编。它可能遗漏非 ASCII 原文或特殊指令编码；定长回填也不能单独证明每个候选都是真实文本。JSON 中的偏移与长度必须来自对应底本，不能跨版本复用。未知变体需另外核验容器结构与代码边界。

控制标记和行宽校验中，部分问题只打印预警；不要把“预检结束”理解为所有问题均硬拦截。换行建议也不是对所有字体和对话框的像素级保证。补充字符可能占两个 UTF-16 码元，不能只用 Python `len()` 估计槽位。

PRS 编解码为 Python 实现，包含文字、短回溯、长回溯及结束标记。最小验证应同时检查 `decompress(compress(data)) == data` 和容器重新解包后的所有成员；不同合法压缩流不必逐字节相同。对损坏输入、压缩预算和未见过的变体仍需专门验证。仓库不附带任务包、大量提取原文、全量翻译记忆或回填成品。

## unitxt：重建指针表与保留条目编号

检索入口：`psobb_unitxt_tool.py` 的 `parse_unitxt_prs`、`build_unitxt_bin`、`export_prs_to_txt`、`import_txt_to_prs`。

unitxt 解压内容由小端 32 位表数量、各表条目数量、字符串指针表及 UTF-16LE 字符串池组成。重建时重新计算指针并为每条字符串写终止符，再 PRS 压缩。导出 TXT 为 UTF-8 BOM，条目结构为：

```text
[00:0000]
自造示例
[/entry]
```

表号和条目号决定运行时索引，不能为排版重新编号。当前导入器会把编号缺口补为空串，重复编号以后出现的内容为准；实际使用前应比较所有表的条目数量、编号唯一性及文本回读结果。不要只检查打包成功，也不要把遗漏编号误当作删除空闲条目的安全方式。

QST 回填和 unitxt 导入都会写入目标文件。复现时使用独立副本和明确的输出路径，保留自备基线；本次技术发布不要求对正在使用的游戏目录执行这些写入操作。
